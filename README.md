# Модель знаний для AI-driven development бекенда

Как давать ИИ-агентам (Claude Code, Codex) контекст по бекенду под конкретную задачу — без полного прохода по проекту и без пропуска неочевидных связей — и держать документацию актуальной. В репозитории: реализация на тестовом проекте, стенд проверки и все артефакты прогонов.

| Где | Что |
|---|---|
| корень | тестовый бекенд с внедрённым решением: `knowledge/`, `tools/knowledge/`, `mcp/`, `docs/`, `AGENTS.md` |
| `eval/` | стенд: эталон, скрытые тесты, скрипты, метрики |
| `eval/artifacts/` | сырые данные каждого прогона |
| `REPORT.md` | краткий отчёт |

---

## 1. Почему граф, а не RAG, и как это соотносится с Memory Bank

**RAG по эмбеддингам** ищет текст, похожий на запрос. Нужные же места связаны с задачей не похожестью, а механизмом: смена площадки заявки аннулирует счёт через событие в другом сервисе, хотя слов «счёт» и «площадка» вместе нигде нет. Обратная проблема — похожие, но не связанные места: в проекте, увеличенном для проверки, у сервиса аренды залов есть своя «смена площадки» с таким же триггером. RAG на стенде не прогонялся; косвенное свидетельство — полнотекстовый поиск точки входа (`find_entry`) предлагал узлы таких двойников в 8 вызовах из 14 (всего 10 позиций, первыми — ни разу), а в пакеты контекста, собранные обходом графа, они не попали ни разу (0 из 1341 узла).

Модель знаний — это Memory Bank, привязанный к коду: факты со ссылками на строки, которые CI сверяет при каждом изменении. Эпизодическая память агента остаётся дополнением для решений и ловушек. **Память Ruflo** как такое дополнение проверена в серии из 5 задач (`eval/artifacts/runs/*-smb1`, выгрузка — `eval/results/ruflo_memory_smb1/`):
- без явной инструкции агенту память не заполняется: Ruflo строит её на автопамяти Claude Code, а агент в коротких задачах ничего туда не пишет;
- с инструкцией «в начале искать, в конце сохранять» агент записал 5 заметок, все по делу; повторно не прочитана ни одна (`access_count = 0`): поиск возвращал заметки из других областей со сходством 0.24–0.29 (модель эмбеддингов по умолчанию — английская all-MiniLM-L6-v2, заметки на русском);
- заметки не связаны с кодом и не сверяются с ним — их нельзя пометить устаревшими при изменении кода.

## 2. Решение

Источник истины — модель системы в репозитории: граф, извлечённый из кода и БД, правила поверх него («как устроено») и бизнес-требования («как должно быть»). Документация для людей и контекст для агента генерируются из неё.

### 2.1. Что делается без LLM

| Скрипт (`tools/knowledge/`) | Источник | Результат |
|---|---|---|
| `extract_db.py` | временная БД после `alembic upgrade head`, `information_schema` + `pg_catalog` | таблицы, FK, CHECK, UNIQUE, частичные индексы, триггеры с телами функций |
| `extract_code.py` | AST, `Base.metadata` SQLAlchemy | символы, вызовы, запись в таблицы, `Depends`, слушатели ORM, константы-настройки, тесты |
| `extract_events.py` | вызовы `publish(...)`, `@subscribe(...)` | топик → издатели → подписчики |
| `extract_bpm.py` | `bpm/*.yaml` | переходы, условия (guards), код условий |
| `requirements.py` | `knowledge/requirements/*.md` | бизнес-требования с ID и хэшем текста |
| `build_index.py` | всё выше + правила + `reconciliation.yaml` | граф в SQLite + полнотекстовый поиск с русским стеммингом; у ребра — способ получения, у правила — профиль достоверности (`trust.py`) |
| `render_docs.py` | граф + правила + требования | `docs/` и блок карты системы в `AGENTS.md` |
| `drift.py`, `check_rules.py` | граф, правила, требования, git diff | CI-проверки (раздел 2.4) |
| `reconcile.py` | всё выше | требования без правил, правила, расходящиеся с требованиями, правила без требования |
| `verify_rule.py` | правила | отметка «проверено человеком»: кто, когда, отпечаток проверенной версии |

### 2.2. Что пишет LLM

- **Правила** (`bootstrap_rules.sh rules <модуль>`): на каждый сервис — новая headless-сессия `claude -p`, на вход — инструкция, срез графа этого модуля и бизнес-требования. Выход — `knowledge/rules/<модуль>.yaml`: ID, текст, ссылки `path::symbol` со строками, ограничения БД, события, тесты, связи с требованиями (`satisfies`, `deviates_from`), оговорки о коде (`caveats`), статус `draft`.
- **Нарезка спецификации на требования** (`knowledge/requirements/*.md`, 102 требования): разово, статус «предложено» до утверждения владельцем.
- **Сверка** требований с правилами и БД → `knowledge/reconciliation.yaml` (на тестовом проекте — 29 расхождений, у каждого `status` и ссылки на требования).
- **Правки правил после изменения кода** — агент-исполнитель по инструкции из `AGENTS.md`.

Человек ставит правилам статус `verified` через `verify_rule.py` (на стенде — выборка 25 из 162; сейчас 22 из 471) и утверждает требования через PR с ревью владельца (`.github/CODEOWNERS`).

### 2.3. Как агент получает контекст

MCP-сервер `mcp/knowledge_server.py`, общий для Claude Code и Codex.

| Инструмент | Ответ |
|---|---|
| `find_entry(текст задачи)` | 8 точек входа в граф, ~350 токенов |
| `impact(узел)` | **пакет контекста**: узлы, достижимые от входного по рёбрам графа (глубина ≤ 4), сгруппированные по видам — требования, правила с пометкой достоверности, переходы и условия процесса, события с подписчиками, ограничения БД, код, настройки, тесты; у каждого — ребро, по которому он найден, и пометка, если связь — предположение. Ограничен бюджетом ~4000 токенов, не вошедшее перечисляется числом |
| `rule(id)` | карточка правила: почему (требования), как (текст), достоверность, где (код, БД, тесты) |
| `requirement(id)` | бизнес-требование: правила, которые его реализуют или расходятся с ним, открытые расхождения |
| `entity(имя)` | карточка таблицы |

Порядок из `AGENTS.md`: `find_entry` → `impact` для 1–3 узлов → чтение кода по ссылкам из пакета → изменение → правка правил. На большом проекте агент делал в среднем 1,1 вызова `find_entry` и 1,9 вызова `impact` на задачу.

**MCP, а не CLI.** Та же функциональность через shell требует от модели собрать команду и разобрать текстовый вывод. Opus 5.5 справлялся и с CLI (в серии с Ruflo все 10 обращений к `ruflo memory search/store` из shell выполнились без ошибок), но для младших моделей типизированный вызов со схемой параметров надёжнее. На стенде младшие модели не проверялись.

### 2.4. Актуальность (CI на каждый PR)

- **Хэши правил.** Для каждой ссылки правила на код хранится хэш нормализованного AST символа вместе с вызываемыми функциями проекта, для ссылки на требование — хэш текста требования. Хэш изменился, а правило в PR не тронуто → правило помечается `suspect` с причиной `code_changed` или `requirement_changed`.
- **Проверка человеком привязана к версии.** У `verified`-правила хранится отпечаток проверенной версии; правило меняли после проверки — оно показывается как устаревшее. `verified` без отпечатка → ошибка.
- **Ссылки на требования** (`satisfies`, `deviates_from`) должны вести на существующие требования; формат требований проверяется.
- **Новое ограничение БД без правила** → ошибка.
- **Модель и `docs/` в PR должны совпадать** с пересобранными из кода.

### 2.5. Требования и достоверность

Бизнес-требования (`knowledge/requirements/*.md`) — «как должно быть»: markdown без технических полей, правят люди. Правила — «как устроено сейчас», извлечены из кода и ссылаются на требования. Расхождения видны по связям: требование без правил — не реализовано (23 из 102), правило с `deviates_from` — расходится (30), правило ядра без требования — поведение, о котором бизнес не знает (14).

Статус правила — этап ревью. Достоверность считается при сборке (`tools/knowledge/trust.py`) по пяти осям: происхождение, способ получения связи (извлечена, указана ИИ, проверена человеком, предположение), актуальность, неоднозначность (D-xx, расхождения, оговорки, вопросы), соответствие требованию. Итог — уровень:

| Уровень | Правил | Что делать агенту |
|---|---|---|
| проверено человеком | 13 | опереться |
| подкреплено кодом и тестами | 318 | опереться |
| без тестов | 77 | сверить с кодом |
| устарело (код, требование или правило менялись после фиксации или проверки) | 0 | сверить с кодом |
| без ссылок на код | 1 | не опираться без проверки |
| расхождение с требованием или открытый вопрос | 62 | уточнить у пользователя |

В контекст агента уходят фразы, а не коды: `[требование REQ-KIND-02 · подкреплено кодом и тестами]`, `[⚠ расходится с REQ-DEDUP-01 (D-01, D-21) — уточни у пользователя]`. Сводка в конце пакета группирует правила по действиям. Цена — около 15 токенов на правило: при бюджете 4000 токенов пакет вмещает 45–50 узлов вместо 50–56. На стенде (раздел 3) эта версия не прогонялась — все цифры экспериментов относятся к версии со статусами.

## 3. Эксперимент

Методика — `eval/docs/evaluation_plan.md`, порядок работ и журнал с отклонениями — `eval/docs/run_scenario.md`.

### 3.1. Стенд

- **Тестовый проект** — ERP библиотеки на Python 3.14, FastAPI, async SQLAlchemy, PostgreSQL, outbox-событиях, процессе в YAML. Сгенерирован вместе с **эталоном** (`eval/ground_truth/`): 68 правил, 20 событий и 48 заранее заложенных неочевидных связей семи типов — правило только в БД, подписчик в другом сервисе, переход только в BPM, поведение из настройки, фоновая задача, слушатель ORM, связь через другую сущность.
- **8 задач** (T01–T07 и контрольная локальная T08) с перечнем затронутых узлов и **скрытыми тестами** (`eval/hidden_tests/`, 47 регрессионных и 23 теста задач). Скрытые тесты копируются в рабочую копию только после завершения сессии исполнителя. Для каждой задачи есть эталонное решение (`eval/reference/`): на исходном коде тесты задачи падают, на эталонном — проходят.
- **Эталон проверен слепым аудитом**: сессия с полным контекстом без доступа к эталону сама перечисляла затронутые узлы по каждой задаче; 34 обоснованные находки добавлены в эталон (`eval/results/blind_audit_vs_ground_truth.md`).
- **Решение внедрено отдельной сессией**, у которой не было доступа к эталону и к плану проверки.

### 3.2. Варианты

| Вариант | Что есть у исполнителя |
|---|---|
| **B1** (базовый) | та же сгенерированная документация в `docs/`, инструкция искать в ней grep'ом; без графа и MCP |
| **S** | модель знаний + MCP + `AGENTS.md` решения |
| **SMB** | S + Ruflo с инструкцией вести память |

Тексты у B1 и S одинаковые: сравнивается способ доставки контекста, а не качество документации.

### 3.3. Масштаб

| | Малый | Большой |
|---|---|---|
| Код | 3,8 тыс. строк, ~45 тыс. токенов | 17,7 тыс. строк, ~170–200 тыс. токенов |
| Граф | 562 узла, 2099 рёбер, 162 правила | 2187 узлов, 7093 ребра, 478 правил |

Большой проект — малый плюс 8 сервисов того же домена (`services/halls`, `subscriptions`, …), сгенерированных по спецификациям `eval/noise/`. В них заложены **двойники** механизмов из задач: своя смена площадки с триггером, свои шаблоны писем со словарём `debt → paid`, свои сроки 30 дней с литералом в фоновой задаче, своя дедупликация. С ядром они не связаны (нет импортов, общих топиков и таблиц), поэтому эталон задач остаётся верным — эталонные решения прошли скрытые тесты и на большом проекте.

### 3.4. Исполнение

Исполнитель — Claude Opus 5.5 в headless-режиме (`claude -p`), изолированный от личных настроек, памяти и MCP-серверов пользователя. Каждый прогон — новая сессия в новом клоне, где есть только ветка варианта. Малый проект: B1 и S × T01, T04, T08 × 2 повтора, уровень усилий по умолчанию; серия SMB — T02 → T03 → T05 → T06 → T07 в одной рабочей копии. Большой проект: B1 и S × T01–T07 × 2 повтора, `--effort medium`.

### 3.5. Метрики

**Детерминированные** (`eval/scripts/collect_run.py`, по файлам прогона):

| Метрика | Как считается | Файлы |
|---|---|---|
| `task_success` | 1, если прошли все скрытые тесты задачи | `junit-hidden.xml` |
| `regressions` | число упавших регрессионных скрытых тестов, кроме тех, что задача заменяет по замыслу (`supersedes` в эталоне задачи) | `junit-hidden.xml`, `ground_truth/tasks/T*.yaml` |
| `hidden_link_recall` | доля скрытых узлов эталона задачи, которые исполнитель **видел**: ID узла есть в ответе MCP; или исполнитель прочитал файл, и в прочитанном тексте есть определение символа; или путь и имя символа встретились в результате поиска; для ограничений БД и топиков — имя в любом результате инструмента | `transcript.jsonl`, `mcp.jsonl` |
| `context_recall` | то же по всем не-правиловым узлам эталона задачи | те же |
| `pack_recall` | доля узлов эталона, попавших в ответы `find_entry`/`impact` | `mcp.jsonl`, `transcript.jsonl` |
| `tokens_context` | сумма токенов (вход + чтение и запись кэша + выход) по уникальным сообщениям модели до первой правки файла — объём обработанного контекста, а не оплаченные токены | `transcript.jsonl` |
| `tokens_total` | то же за всю сессию (итог Claude Code) | `transcript.jsonl` |
| `cost_usd` | `total_cost_usd` из итога Claude Code — стоимость по ценам API (прогоны шли по подписке) | `transcript.jsonl` |
| `files_read_whole` | вызовы `Read` без диапазона по файлам длиннее 200 строк + `cat` в shell | `transcript.jsonl` |
| размер пакета | `response_tokens` (длина ответа / 3) и число узлов в `nodes_returned`; отсечённые узлы — из строки «Не вошло по бюджету» | `mcp.jsonl`, `transcript.jsonl` |

**LLM-оценки** (аудитор — отдельная сессия Claude, только чтение, `eval/agents/context-auditor.md`):
- **Качество модели знаний.** Аудитор сопоставил каждое правило эталона с правилами модели (полностью — 1, частично — 0.5, нет — 0) → rule recall; оценил каждое правило модели по коду (верно / частично / неверно) → precision.
- **Doc QA.** Одна сессия отвечала на 30 вопросов, видя только `docs/`, другая сверяла ответы с эталонными.
- **Precision пакета и полнота плана** — только в малом пилоте, в выводах не используются.

**Мутации CI** (`eval/scripts/run_mutations.sh`). Шесть правок кода «как в PR» без обновления модели и контроль без изменений. На каждой — шаги CI решения. Сигнал = `drift.py` вернул ошибку или пометил правила `suspect`, либо упал `check_rules.py`. Требование пересобрать модель из-за сдвига строк считается отдельно — оно срабатывает на любую правку кода.

### 3.6. Ограничения эксперимента

- Оба проекта (до ~200 тыс. токенов) помещаются в контекстное окно модели. Кодовые базы, которые в окно не помещаются, не проверялись.
- По 2 повтора на вариант. Разброс между повторами заметный: например, стоимость T01 у B1 на большом проекте — $1.92 и $1.16.
- Малый и большой проект прогонялись с разным уровнем усилий модели (по умолчанию и `medium`), поэтому сравнение «малый → большой» внутри варианта сдвинуто этим различием. Сравнение B1 и S внутри одного проекта корректно.
- LLM-оценки (качество модели знаний, Doc QA) выставлены моделью того же семейства, что исполнитель, и вручную не проверялись. Выводы о доставке контекста опираются только на детерминированные метрики.
- Задача T01 похожа на пример из описания решения, по которому решение отлаживалось при внедрении.
- Серия SMB — один прогон на задачу и без парных прогонов S на тех же задачах.

### 4.6. Модель знаний при росте проекта

При bootstrap на большом проекте модель потеряла две связи из задач:
- **ссылка правила T01 на триггер** `forbid_venue_change` стала неоднозначной из-за двойника `halls.forbid_venue_change` — CI решения выдал ошибку, ссылка исправлена по ней;
- **связь T02 «литерал 30 в фоновой задаче ↔ `LOAN_PERIOD_DAYS`»** перестала выводиться, когда в проекте появилось несколько настроек со значением 30, — модель потеряла её без сигнала.

Исполнитель S в обоих случаях нашёл связи сам, чтением кода.

## 5. Выводы

1. **Полнота модели.** Граф из детерминированных экстракторов плюс правила, извлечённые LLM по срезам модулей, покрывает почти все заложенные связи, включая живущие только в БД, событиях и описании процесса. Слабее всего — фоновые задачи (0.88).
2. **Малый проект.** S не уступает базовому варианту ни в полноте, ни в стоимости. Обрабатывает больше токенов, потому что пакет добавляется к чтению файлов.
3. **Рост проекта.** У базового варианта сбор контекста с ростом проекта растёт (+32% токенов, больше файлов целиком): grep находит и двойников. У S размер пакета от проекта не зависит, сбор контекста не растёт, файлов читается вдвое меньше, чем у базового. По стоимости на проекте в 4–5 раз больше варианты пока равны (−4% у S). Экономия на кодовых базах, не помещающихся в окно, следует из этого механизма, но на стенде не измерялась.
4. **Длинные цепочки.** На задаче с цепочкой через процесс и события S стабильно находит все связи, базовый — нет.
5. **CI** ловит значимые изменения кода без обновления модели, включая перенос логики во вспомогательную функцию. Ложные тревоги — на переименование локальных переменных.
6. **Что доработать:**
   - отбирать узлы пакета по релевантности задаче, а не только по глубине, и включать фрагменты кода, чтобы агенту не приходилось открывать файлы целиком;
   - квалифицировать имена объектов БД и кода схемой или модулем;
   - сигнализировать, когда вывод связи стал неоднозначным, вместо её молчаливой потери;
   - нормализовать локальные имена в хэшах;
   - проверять события без подписчиков;
   - хранить ссылки на код без номеров строк;
   - прогнать на стенде версию с требованиями и фразами о достоверности: понимает ли агент пометки и не
     теряет ли он узлы из-за их стоимости в бюджете;
   - решить, вести ли обход от правила к соседним правилам того же требования (сейчас нет: это может
     добавить межсервисные связи «по смыслу», но и шум в пакет).
