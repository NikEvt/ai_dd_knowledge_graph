# Сверка трёх источников: общая схема, код, БД

Ты аналитик. Проект ERP библиотеки реализует **подмножество** общей схемы бизнес-процессов
(`knowledge/sources/erp-library.md`) с упрощениями. Правила из кода и БД уже извлечены (список ниже),
детерминированная сверка нашла кандидатов в расхождения (ниже). Твоя задача — сверить схему с ними.
Код не исправляется: расхождения только фиксируются.

Инструменты: только Read, Grep, Glob. Прочитай схему целиком; код читай точечно, чтобы проверить гипотезу.

## Что сделать

1. **Бизнес-требования (`knowledge/requirements/*.md`), у которых нет реализующих правил.**
   - Если нашёл реализацию в коде/БД, которую пропустили, — правило с ID `R-SCHEMA-<ТЕМА>-NN`,
     `status: draft`, `satisfies` (или `deviates_from` с `note`), `implemented_by` / `enforced_by_db`
     (ID символов, переходов и объектов БД — точно как в модели: `путь::имя`, `from->to`, имя объекта БД).
   - Если реализации нет — правило не создавай: требование без правил само видно как «не реализовано».
     Если это важно — заведи расхождение (п. 2).
   Не дублируй правила, которые уже есть в списке (пусть и с другой формулировкой).
2. **Расхождения** — где схема, код и БД говорят разное (в т.ч. из детерминированной сверки:
   ограничения БД без правил, литералы вместо настроек, роли, которые код не проверяет, мёртвые ветки).
   Для каждого: `id: D-NN`, `title`, `schema` (что в схеме, со ссылкой §), `code` (что делает код,
   `путь::символ:строки`), `db` (что в БД, если причастна), `requirements` (ID требований), `rules` (ID
   связанных правил), `status: open`, `severity`
   (`high` — нарушение бизнес-правила возможно на практике, `medium` — расхождение в краевых случаях,
   `low` — упрощение проекта, ожидаемое), `question` — вопрос владельцу процесса.

## Формат вывода

Только один блок ```yaml:

```yaml
rules:
  - id: R-SCHEMA-LINK-01
    title: По ссылке нельзя изменить данные заявки
    text: >
      Публичные эндпоинты ссылки позволяют только смотреть окна, записываться, переносить и отменять визит.
    kind: constraint
    roles: [client, representative]
    implemented_by:
      - symbol: services/scheduling/api.py::book
    satisfies:
      - requirement: REQ-BOOK-06
    status: draft
discrepancies:
  - id: D-01
    title: Срок пользования книгами задан литералом в фоновой задаче
    schema: "§14: срок пользования — месяц с даты выдачи"
    code: "services/scheduling/jobs.py::flag_overdue:16 — timedelta(days=30) вместо settings.LOAN_PERIOD_DAYS"
    db: ""
    requirements: [REQ-RETURN-01, REQ-FINE-04]
    rules: [R-SCHED-LOAN-01]
    status: open
    severity: medium
    question: Должна ли просрочка считаться от due_at выдачи (LOAN_PERIOD_DAYS), а не от литерала?
```
