# Извлечение бизнес-правил из одного модуля

Ты аналитик. Задача — извлечь из **одного модуля** ERP библиотеки бизнес-правила и записать их в
машиночитаемом виде. Правила попадут в модель знаний, по которой другие агенты будут собирать
контекст перед изменениями. Ошибка в ссылке на код хуже, чем пропущенное правило.

Модуль: `{{MODULE_PATH}}`. Префикс ID: `R-{{PREFIX}}-`.

## Входные данные

1. **Срез графа модуля** (ниже, после промпта) — получен статическим анализом кода и интроспекцией БД:
   символы с номерами строк, проверки (`raise DomainError/AccessDenied/...` с условием), вызовы,
   события (кто публикует и кто обрабатывает — в т.ч. в других сервисах), переходы процесса заявки,
   настройки, таблицы с ограничениями и триггерами БД, тесты.
2. **Код** — читай файлы инструментом Read, чтобы проверить формулировку и номера строк.
   Срез — карта, а не замена кода.
3. **Общая схема бизнес-процессов** — `knowledge/sources/erp-library.md`. Проект реализует её
   подмножество с упрощениями. Прочитай разделы, относящиеся к модулю.

Инструменты: только Read, Grep, Glob. Ничего не меняй в репозитории.

## Что считать правилом

Одно правило — одно проверяемое утверждение о поведении системы. Ищи в первую очередь связи,
**которых не видно по импортам**:

- проверки и запреты в коде (условие + сообщение ошибки), права ролей (кто может действие);
- ограничения и триггеры БД на таблицах модуля (что запрещает, чем дублирует или дополняет код);
- побочные эффекты через события: модуль публикует событие → что делают подписчики в других сервисах
  (и наоборот: на какие чужие события реагирует модуль и что делает);
- условия процесса (`guard`) и переходы между этапами, которые выполняет модуль;
- фоновые задачи и таймеры (точка отсчёта, срок, какая настройка; **если срок задан литералом,
  а не настройкой — отметь это**);
- настройки и константы модуля, влияющие на поведение (группы этапов, шаблоны, лимиты);
- слушатели ORM (`before_flush` и т.п.) — что они делают неявно;
- расчёты (сумма счёта, надбавка, срок возврата).

Не нужны: технические детали без бизнес-смысла (DTO, сериализация, `NotFound` для несуществующего id).
Ориентир — 15–40 правил на модуль, без дублей.

## Формат вывода

Выведи **только один** блок ```yaml со списком `rules:` и ничего больше. Пример записи:

```yaml
rules:
  - id: R-APP-VENUE-CHANGE-03
    title: Смена площадки аннулирует неоплаченный счёт
    text: >
      При смене площадки платной заявки действующий счёт за книги без привязанных платежей
      аннулируется (подписчик billing на application.venue_changed), заявка возвращается
      в «Ожидает счёта», бухгалтер выставляет новый счёт по прайсу и реквизитам новой площадки.
    kind: effect            # guard | permission | effect | timer | invariant | calculation | config
    applies_to: [application.kind=paid]
    trigger: event:application.venue_changed
    effects:
      - "invalidates: table:billing.invoices"
      - "transition:awaiting_payment->awaiting_invoice"
    roles: [operator]       # кто выполняет действие (operator, reviewer_lead, reviewer, accountant,
                            # chief_accountant, site_checker, admin, client, representative, system)
    related: [R-APP-VENUE-CHANGE-01]
    implemented_by:
      - symbol: services/billing/consumers.py::on_venue_changed
        lines: 13-16
      - transition: awaiting_payment->awaiting_invoice
    enforced_by_db:
      - constraint: trg_invoices_cancel_guard
    config: []
    tested_by:
      - tests/test_venue_change.py::test_venue_change_before_payment_reissues_invoice
    schema_ref: "§7 Смена площадки"
    discrepancy: >
      Схема: после оплаты площадку меняют только через возврат. Код: счёт с частичной оплатой
      не аннулируется, площадка меняется — счёт остаётся на реквизитах старой площадки.
    status: draft
```

Требования к полям:

- `id` — `R-{{PREFIX}}-<ТЕМА>-NN`: тема латиницей КАПСОМ через дефис (VENUE-CHANGE, INVOICE, ARCHIVE…),
  NN — двузначный номер внутри темы. ID уникальны.
- `title` — короткое утверждение по-русски; `text` — 1–4 предложения по-русски: что, когда, где реализовано.
- `implemented_by` — обязательно хотя бы одна ссылка на код или процесс, если правило реализовано:
  - `symbol` — ID символа **точно как в срезе** (`путь::имя`), `lines` — диапазон строк проверки
    или эффекта в этом символе (проверь Read'ом);
  - `transition` — переход **точно как в срезе** (`from->to`), `guard` — `guard:<имя>`.
- `enforced_by_db` — имена объектов БД **точно как в срезе** (триггер, функция, CHECK, индекс):
  `- constraint: <имя>`. Ограничение без кода тоже правило — опиши его.
- `config` — ID настроек как в срезе (`libs/settings.py::LOAN_PERIOD_DAYS`).
- `tested_by` — ID тестов как в срезе; не выдумывай тесты.
- Ссылки в `trigger`/`effects` пиши с префиксом типа: `event:<topic>`, `transition:<from->to>`,
  `table:<schema.table>`, `symbol:<id>`, `config:<id>`, `role:<role>`, `stage:<stage>`.
- `schema_ref` — раздел схемы (`§11 Счета`), если правило там описано.
- `discrepancy` — только если поведение кода/БД расходится со схемой: что сказано в схеме, что делает
  код. **Описывай фактическое поведение кода в `text`**, расхождение — в `discrepancy`. Код не исправляй.
- `status` — всегда `draft`. Поле `hash` не заполняй — его посчитает скрипт.
- Все строковые значения — в YAML-корректном виде (кавычки для строк с `:` или `#`).
