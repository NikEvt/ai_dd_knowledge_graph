# AI-driven development для бекенда ERP библиотеки

**Контекст:** 3 бекенд-разработчика работают через Claude Code и Codex. Полной документации нет. Ограничения размазаны между кодом и БД (около 50 таблиц).

**Цели:**
1. Иметь человекопонятную полную документацию и поддерживать её при каждом изменении.
2. Давать агенту ровно тот контекст, который нужен под задачу: дёшево по токенам и без пропуска неочевидных связей.

---

## 1. Диагноз: почему «папка md + grep» не работает

Главная сложность проекта не в объёме кода, а в **сквозных бизнес-правилах**. Одно действие запускает цепочку последствий в сущностях, которые лексически никак не связаны. Примеры из схемы проекта:

| Действие | Что затрагивает | Почему grep пропустит |
|---|---|---|
| Смена площадки | аннулирование счёта, отмена записи и письма, освобождение книг, смена проверяющего оператора, проверка наличия сферы, возврат платежа после оплаты, разные сроки для разных видов заявок | последствия живут в модулях счетов, расписания, писем и назначений, где слова «площадка» может не быть |
| Обновление данных клиента | перепроверка **других** заявок клиента, но только тех, что не дошли до записи | связь идёт через клиента, а не через заявку |
| Дедупликация заявок | автозакрытие второй заявки по той же сфере. Момент срабатывания разный: платная при оплате, «в долг» при прохождении проверки. Между социальной и платной правило не действует | правило срабатывает как побочный эффект двух разных событий |
| Заявка «в долг» и письма | использует шаблоны **платных** заявок | в коде писем нет слова «долг» |
| Таймеры архива | разные точки отсчёта (начало проверки или выставление счёта), сброс после возврата из архива | таймер в фоновой задаче, а правило в процессе заявки |

Из этого следуют два вывода:

- **grep ищет по словам, а связи здесь проходят по смыслу.** Чем точнее агент ищет, тем увереннее он пропускает неочевидное.
- **Принудительный cat всех md решает проблему полноты ценой токенов** и всё равно не гарантирует, что модель свяжет правило из одного файла с кодом из другого.

Нужен не набор текстов, а **граф знаний о системе**, по которому связи проходят явно.

## 2. Принцип: единая модель знаний, документация как производная

```
             ┌──────────────────────────────────────┐
  БД ───────▶│                                      │──▶ документация для людей (генерируется)
  код ──────▶│   Модель знаний (граф) в репозитории │──▶ context pack для агента (по запросу)
  правила ──▶│                                      │──▶ проверки в CI (drift, покрытие)
             └──────────────────────────────────────┘
```

- Источник истины один: **машиночитаемая модель домена**, которая хранится в репозитории и проходит code review наравне с кодом.
- Документация для людей **не пишется руками отдельно**, а рендерится из модели. Поэтому она не может разойтись с тем, что видит агент.
- Агент не читает документацию целиком. Он **запрашивает срез графа** под задачу.

## 3. Модель знаний

### 3.1. Узлы

| Тип | Примеры | Источник |
|---|---|---|
| `table`, `column` | `applications`, `applications.venue_id` | интроспекция БД |
| `db_constraint` | FK, CHECK, UNIQUE, триггеры, функции | интроспекция БД |
| `status`, `transition` | `draft → on_review`, `awaiting_payment → awaiting_issue` | код + правила |
| `role`, `permission` | оператор может сменить площадку до оплаты | правила |
| `rule` | бизнес-правило со стабильным ID | правила + извлечение из кода |
| `symbol` | сервис, хендлер, фоновая задача, ORM-модель | статический анализ |
| `effect` | письмо, событие в чате, таймер, освобождение книг | код + правила |
| `test` | тест, проверяющий правило | код |

### 3.2. Рёбра

`reads`, `writes`, `guards` (правило запрещает переход), `triggers` (событие запускает эффект), `invalidates` (аннулирует счёт или отправляет на перепроверку), `notifies`, `implemented_by`, `enforced_by_db`, `tested_by`.

### 3.3. Пример записи правила

```yaml
id: R-VENUE-CHANGE-03
title: Смена площадки при выставленном, но неоплаченном счёте
text: >
  Если счёт уже выставлен, но не оплачен, при смене площадки он аннулируется
  и выставляется заново по прайсу и реквизитам новой площадки.
applies_to: [application.kind=paid]
trigger: transition:application.venue_changed
effects:
  - invalidates: invoice.active_books_invoice
  - requires: role:accountant -> action:issue_invoice
related: [R-VENUE-CHANGE-01, R-INVOICE-ONE-ACTIVE, R-INVOICE-PRICE-FIXED]
implemented_by:
  - symbol: services/venue.py::change_venue
    hash: 9f3c2a1
enforced_by_db:
  - constraint: uq_invoice_one_active_per_application
tested_by:
  - tests/venue/test_change_venue.py::test_R_VENUE_CHANGE_03
status: verified   # draft | verified | suspect
```

Поля `hash` нужны для отслеживания устаревания (раздел 6). Для 50 таблиц и нескольких сотен правил не нужна графовая СУБД: достаточно YAML-файлов в репозитории и индекса в SQLite, который собирается скриптом.

### 3.4. ID правил как средство трассируемости

Каждое правило связывается с кодом и тестами по ID:

```python
# @rule R-VENUE-CHANGE-03
def change_venue(application, new_venue): ...
```

После этого grep становится надёжным инструментом: он ищет **по идентификатору, а не по формулировке**. Это прямой ответ на проблему «grep что-то пропускает».

## 4. Bootstrap: как наполнить модель без документации

Принцип: **детерминированно всё, что можно, через LLM только то, что нельзя**, и всегда со ссылкой на источник.

| Шаг | Что делаем | Инструмент | Стоимость |
|---|---|---|---|
| 1. БД | таблицы, колонки, FK, CHECK, UNIQUE, триггеры, функции | скрипт по `information_schema` и `pg_catalog` (или аналогам) | без токенов, точно |
| 2. Код | граф вызовов, карта «какой код пишет в какую таблицу» через ORM-модели, фоновые задачи | tree-sitter, LSP или SCIP-индекс | без токенов, точно |
| 3. Правила из схемы | разбор имеющейся общей схемы на правила с ID | LLM + ревью человеком | разово |
| 4. Правила из кода | LLM проходит **по одному модулю за раз**, получая на вход срез графа из шагов 1–2, и извлекает проверки, guard-условия, побочные эффекты. Каждое правило обязано содержать ссылку на строки кода | LLM + ревью человеком | разово, по модулям |
| 5. Сверка | сравнение трёх источников (схема, код, БД) | скрипт + LLM для формулировок | разово, затем в CI |

Шаг 5 даёт отдельную ценность: он находит **скрытые ограничения и противоречия**.

- Правило есть в схеме, но не найдено в коде → либо не реализовано, либо реализовано неочевидно.
- Ограничение есть в БД, но не описано → скрытое правило, его нужно сформулировать.
- Проверка в коде дублирует триггер БД → кандидат на упрощение или источник расхождений.
- Проверка в коде противоречит схеме → вопрос к владельцу бизнес-процесса.

Правила, извлечённые LLM, получают статус `draft`. Статус `verified` ставит только человек. Агент видит статус и учитывает уровень доверия.

## 5. Доставка контекста агенту

### 5.1. MCP-сервер над моделью знаний

Один MCP-сервер обслуживает и Claude Code, и Codex. Основные инструменты:

| Инструмент | Что делает |
|---|---|
| `find_entry(task_text)` | превращает формулировку задачи в узлы графа: таблицы, правила, статусы. Здесь уместны эмбеддинги, **но только для поиска точки входа** |
| `impact(node, depth=2)` | обходит граф от узла по рёбрам и возвращает **context pack** |
| `rule(id)` | полный текст правила, его реализации, ограничения БД, тесты |
| `entity(name)` | карточка сущности: поля, ограничения, статусы, правила |
| `who_can(action)` | роли и условия для действия |

Это гибридный подход, и выбор сделан осознанно: **эмбеддинги находят похожее, граф находит связанное.** Чистый RAG по векторам здесь не подходит: «смена площадки» и «аннулирование счёта» семантически далеки, но жёстко связаны.

### 5.2. Context pack

Ответ `impact` — компактный документ на 2–5 тысяч токенов вместо десятков файлов:

1. Затронутые правила (текст + статус `verified` / `draft`).
2. Таблицы и ограничения БД, которые могут сработать.
3. Точки входа в код (файл и символ, без содержимого).
4. Побочные эффекты: письма, события в чате, таймеры.
5. Тесты, которые нужно прогнать или дописать.
6. Пометки `suspect`, если правило могло устареть.

Код агент читает сам и точечно: он уже знает, какие символы открывать.

### 5.3. Уровни контекста (progressive disclosure)

| Уровень | Что | Как попадает в контекст |
|---|---|---|
| L0 | карта системы на одну страницу: сущности, статусы, роли, правило работы с MCP | всегда, через CLAUDE.md / AGENTS.md |
| L1 | карточки сущностей и процессов | по запросу `entity`, `impact` |
| L2 | полные тексты правил, код, ограничения БД | по запросу `rule`, чтение файлов |

### 5.4. Субагент-разведчик

Сбор контекста выполняет отдельный субагент в **своём** окне: вызывает `find_entry` и `impact`, точечно читает код, проверяет гипотезы. Основному агенту он возвращает сжатую выжимку. Основное окно не забивается промежуточным чтением, а дорогая модель тратит токены на решение, а не на поиск.

### 5.5. Инструкция для агента (фрагмент AGENTS.md)

```md
## Перед любым изменением
1. Вызови find_entry с текстом задачи.
2. Вызови impact для каждого найденного узла.
3. В плане явно перечисли затронутые правила по ID.
   Если правило в статусе draft или suspect — отметь это как риск.
4. Не читай файлы целиком, если impact указал конкретные символы.

## После изменения
5. Обнови аннотации @rule в изменённом коде.
6. Если изменилось поведение — предложи правку правила в knowledge/rules/.
```

## 6. Поддержание актуальности

Без этого слоя любая модель знаний устаревает за несколько недель. Поддержка встроена в обычный процесс PR, а не вынесена в отдельную обязанность.

### 6.1. Конвейер в CI на каждый PR

```
PR ──▶ пересборка слоёв БД и кода ──▶ diff графа
                                          │
             ┌────────────────────────────┼────────────────────────────┐
             ▼                            ▼                            ▼
   изменились символы,          новая миграция БД          новый код без
   связанные с правилами        без описания в модели      аннотации @rule
             │                            │                            │
             └──────────────▶  агент предлагает правку модели  ◀───────┘
                                          │
                                          ▼
                             ревью человеком вместе с кодом
                                          │
                                          ▼
                             перегенерация документации
```

### 6.2. Drift detection через хэши

У каждого правила хранятся хэши фрагментов кода, которые его реализуют. Изменился хэш, а текст правила в том же PR не тронут → правило получает статус `suspect`, PR получает предупреждение. Это дешёвая детерминированная проверка без LLM.

### 6.3. Правила для CI

| Проверка | Действие |
|---|---|
| изменён код правила, правило не обновлено | предупреждение + `suspect` |
| миграция добавляет ограничение, не описанное в модели | блокировка PR |
| правило без `implemented_by` | отчёт о покрытии |
| правило без `tested_by` | отчёт о покрытии |
| `suspect` старше двух недель | задача на разбор |

### 6.4. Генерация документации для людей

Из модели автоматически рендерятся:

- страницы сущностей: поля, ограничения, статусы, связанные правила;
- страницы процессов: путь заявки по видам, архив и попытки;
- матрица «кто что может» по ролям;
- диаграммы статусов в Mermaid;
- отчёт о покрытии и устаревших правилах.

Документация всегда согласована с моделью, потому что построена из неё. Правка «руками» в сгенерированные файлы запрещена: правят модель.

## 7. Рабочий процесс команды

```
задача
  │
  ▼
find_entry → impact (субагент) → context pack
  │
  ▼
план: перечень затронутых правил по ID, риски по draft/suspect
  │
  ▼
код + аннотации @rule + тесты по ID правил
  │
  ▼
PR: diff графа, drift-проверки, предложенная правка модели
  │
  ▼
ревью кода и модели вместе → merge → перегенерация документации
```

Организационные договорённости:

- **Одни инструкции для обоих агентов.** CLAUDE.md и AGENTS.md — один файл (симлинк), MCP-сервер общий.
- **Модель знаний — код.** Правки модели проходят ревью так же, как код.
- **Владелец модели не нужен.** Каждый PR обновляет модель в зоне своих изменений, CI не даёт об этом забыть.
- **Внедрение по шагам.** Сначала слой БД и ID правил из схемы (дни работы), затем граф кода, затем извлечение правил по модулям по мере того, как в них приходят задачи.

### Метрики

| Метрика | Зачем |
|---|---|
| токены на задачу (сбор контекста / решение) | эффект от context pack |
| пропущенные зависимости, найденные на ревью или в проде | качество impact |
| доля правил `verified` / `draft` / `suspect` | здоровье модели |
| покрытие правил кодом и тестами | полнота документации |

## 8. Пример: задача «разрешить смену площадки для социальной заявки после формирования ссылки на запись»

**Шаг 1. `find_entry`** находит узлы: `transition:application.venue_changed`, `application.kind=social`, `R-VENUE-CHANGE-*`.

**Шаг 2. `impact(R-VENUE-CHANGE-05, depth=2)`** возвращает context pack:

```md
## Правила
- R-VENUE-CHANGE-05 [verified] Социальная и «в долг»: смена площадки только до
  формирования публичной ссылки на запись. ← изменяется
- R-VENUE-CHANGE-06 [verified] Если клиент уже записан: запись отменяется, книги
  освобождаются, клиенту и представителю уходит письмо об отмене и новая ссылка.
  ← раньше для социальных не срабатывало, теперь сработает
- R-VENUE-CHANGE-04 [verified] На новой площадке должна быть сфера заявки.
- R-VENUE-CHANGE-07 [verified] Назначается проверяющий оператор новой площадки.
- R-VENUE-CHANGE-08 [verified] После выдачи книг смена площадки запрещена.
- R-MAIL-TEMPLATES-02 [verified] Шаблоны писем — по площадке и виду заявки.
  Для новой площадки нужен шаблон отмены для социальных заявок.
- R-BOOKS-RELEASE-01 [draft] Книги освобождаются при смене площадки. ← проверить

## Ограничения БД
- chk_venue_change_allowed (CHECK по статусу и виду заявки) ← блокирует изменение
- trg_booking_release_books (триггер освобождения книг при отмене записи)

## Код
- services/venue.py::change_venue
- services/booking.py::cancel_booking
- services/mail.py::send_cancellation
- jobs/assignments.py::reassign_site_checker

## Эффекты
- письмо об отмене + новая ссылка, событие в чате заявки

## Тесты
- tests/venue/test_change_venue.py (R-VENUE-CHANGE-05, -06)
```

**Что это даёт.** Агент сразу видит четыре неочевидные вещи:

1. Изменение нужно делать в двух местах: в коде и в CHECK-ограничении БД.
2. Для социальных заявок впервые начнёт срабатывать ветка отмены записи с письмами.
3. На новой площадке может не оказаться шаблона письма для социальных заявок.
4. Правило об освобождении книг в статусе `draft`, его надо проверить, а не принять на веру.

Ни одно из этих мест не находится grep по слову «социальная», а полный проход по проекту стоил бы на порядок больше токенов.

**Шаг 3. PR** содержит код, миграцию CHECK, новый текст `R-VENUE-CHANGE-05`, подтверждённый `R-BOOKS-RELEASE-01` и тест. CI пересобирает граф, drift-проверки проходят, документация перегенерируется.

## Итог

| Проблема | Решение |
|---|---|
| нет документации | bootstrap: интроспекция БД и кода без LLM, извлечение правил LLM по модулям со ссылками на код, сверка трёх источников |
| документация устаревает | документация генерируется из модели, модель обновляется в каждом PR, drift через хэши в CI |
| grep пропускает связи | связи хранятся явно в графе, трассируемость через ID правил |
| полный проход сжигает токены | `impact` возвращает context pack на 2–5 тысяч токенов, сбор контекста в субагенте |
| два разных агента | общий MCP-сервер и единый AGENTS.md / CLAUDE.md |
