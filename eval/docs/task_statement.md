# Формулировка задачи

Источники: `task_context.md` (условие тестового задания), `erp-library.md` (общая схема проекта — бизнес-правила ERP коммерческой библиотеки) и стек команды (раздел 3).

---

## 1. Что нужно сделать

Описать своё видение **AI-driven development** для бекенд-проекта: как команда, которая пишет код через Claude / Codex, внедряет и поддерживает ИИ-контекст по большому проекту со сложными связями.

Решение должно закрыть две проблемы:

1. **Документация.** Получить человекопонятную и полную документацию проекта и держать её актуальной, когда функционал меняется или расширяется.
2. **Контекст для нейросети при новой задаче.** Когда разработчик берёт задачу, агент должен получить нужный контекст, в том числе узнать, на какие другие блоки влияет изменение. При этом агент не должен:
   - каждый раз проходить весь проект целиком (это сжигает много токенов);
   - пропускать неочевидные связи между блоками.

---

## 2. Цель

Сделать процесс, при котором:

- документация полная, понятна человеку и не отстаёт от кода;
- агент на новой задаче быстро и дёшево по токенам получает **достаточный и точный** контекст, включая косвенные зависимости;
- риск, что изменение одного блока незаметно сломает другой, снижается.

Главное в ответе — **методы внедрения ИИ-контекста в сложный проект**, а не декомпозиция самого проекта.

## 4. Ограничения

1. **Решение «куча md-файлов» не подходит.** Проект большой, связей много: grep будет пропускать связи, а принудительное чтение файлов (`cat`) тратит токены впустую.
2. **Генерация кода по md не нужна.** Подход «пишем спецификацию — по ней генерируем код» в задачу не входит.
3. **Декомпозиция проекта — не основа ответа.** Разбиение системы на модули можно упоминать, но ответ должен быть про методы работы с контекстом.
4. **Нужно учитывать два источника истины:** код и БД. Правила, которые есть только в схеме БД (связи, ограничения таблиц), тоже должны попасть в документацию и в контекст агента.
5. **Решение должно подходить для команды из трёх человек.** Его поддержка не должна стать отдельной работой на полный день.
6. **Решение должно быть универсальным.** Подход не должен быть привязан к конкретному стеку и должен переноситься на другие проекты. Примеры и иллюстрации — на стеке команды (раздел 3).

## 5. Средства

- **Claude и Codex** (Claude 5 Opus, ChatGPT 5.6) — основные инструменты, ими пользуются разработчики. Решение должно работать с обоими или объяснять, как оно на них ложится.
- **Инструменты, которые уже есть у команды:** фреймворк Ruflo, Memory Bank, Ruff. Решение должно учитывать их: встроиться, дополнить или обоснованно заменить.
- **Входные данные для контекста:** исходный код (Python 3.14, FastAPI, async SQLAlchemy), схема БД (около 50 таблиц), бизнес-правила из `erp-library.md`.
- Выбор конкретных механизмов (индексы, графы связей, инструменты/серверы для агентов, автоматизация обновления документации и т.д.) — часть решения. Условие их не задаёт и не запрещает, кроме ограничений из раздела 4.
- Механизмы описываются в общем виде (универсальность), а конкретная реализация показывается на примере стека команды.

## 6. Почему связи здесь сложные (примеры из `erp-library.md`)

На этих сценариях можно проверить, находит ли решение неочевидные зависимости. Изменение в одном месте задевает сразу несколько блоков:

- **Смена площадки** → аннулируется и заново выставляется счёт (прайс и реквизиты новой площадки), отменяется запись на визит, освобождаются книги, уходит письмо об отмене и новая ссылка, назначается другой проверяющий оператор, проверяется, есть ли сфера на новой площадке. Ограничения зависят от вида заявки (платная — до оплаты, остальные — до публичной ссылки).
- **Обновление данных клиента** → все другие заявки клиента, не дошедшие до записи, возвращаются на проверку.
- **Две заявки клиента по одной сфере** → вторая закрывается автоматически как дубль, её счёт аннулируется. Момент срабатывания разный для платной (полная оплата) и заявки в долг (прохождение проверки). Для пары «социальная + платная» правило не действует.
- **Архив и попытки** → разные автоматические сроки для разных видов заявок, перезапуск месяца на оплату при возврате из архива, повторный счёт только если изменилась сумма.
- **Права ролей** → права зависят от роли, от того, кто закреплён за заявкой, от площадки (проверяющий оператор) и от этапа заявки.
- **Админка** → надбавки, штрафы, работа в долг, шаблоны писем и лимиты мест влияют на расчёты и поведение заявок, но уже выставленные счета не пересчитываются.

Архитектура стека добавляет свои источники неявных связей (это вывод из стека, а не из условия):

- **Микросервисы** → связь между блоками может проходить через границу сервисов: правило в одном сервисе, данные в другом.
- **Event-Driven** → издатель и подписчик события напрямую в коде не связаны. Grep по имени функции не покажет, кто реагирует на событие (например, «заявка оплачена» → закрытие дубля, открытие записи, письма, событие в чате).
- **BPM** → порядок этапов и переходы могут описываться процессами, а не только кодом. Это третий источник истины рядом с кодом и БД.

## 7. Формат результата

- **Текстовый файл или md-файл** с описанием подхода.
- Ожидаемое содержание:
  1. Как получить и поддерживать полную человекопонятную документацию (в том числе как она обновляется при изменениях в коде и БД).
  2. Как агент получает контекст по новой задаче: откуда берёт, как находит затронутые блоки и косвенные связи, как экономит токены.
  3. Почему подход надёжнее «кучи md + grep»: за счёт чего связи не теряются.
  4. Как подход встраивается в ежедневную работу трёх разработчиков с Claude / Codex и в уже используемые инструменты (Ruflo, Memory Bank, Ruff).
- Подход описывается универсально. Примеры показываются на стеке команды и, где уместно, на домене `erp-library.md`.
- Не нужно: код системы, генерация кода по документации, подробная декомпозиция предметной области.

## 8. Что не определено в условии (допущения)

В исходных файлах этого нет. Решение должно либо работать без этой информации, либо явно оговорить допущение:

- тип СУБД и где именно в ней лежит логика (внешние ключи, ограничения, триггеры, процедуры);
- сколько сервисов, как они делят БД (общая или своя у каждого) и через что ходят события (брокер, формат и реестр схем событий);
- чем реализован BPM (движок процессов или код);
- как сейчас используются Ruflo и Memory Bank и что в Memory Bank уже лежит;
- есть ли тесты, CI и code review;
- бюджет на токены и инфраструктуру.
