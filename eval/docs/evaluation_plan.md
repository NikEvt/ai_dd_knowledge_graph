# План проверки решения на тестовом проекте

Цель: на сгенерированном тестовом проекте измерить, работают ли из `ai-driven-development_suggested_solution.md`:
- документирование (модель знаний и сгенерированная документация);
- сохранение контекста (актуальность модели при изменениях);
- получение контекста (`find_entry` / `impact` / context pack).

Измерять нужно числами и в сравнении с базовыми вариантами, а не на глаз.

---

## 1. Тестовый проект: что заложить при генерации

Главное требование: **у тестового проекта должна быть эталонная разметка (ground truth)**. Мы генерируем проект сами, поэтому знаем каждое правило, где оно реализовано и с чем связано. Без эталона recall не посчитать.

### 1.1. Состав

- Стек команды: Python 3.14, FastAPI, async SQLAlchemy, Alembic, PostgreSQL.
- 4–6 микросервисов на подмножестве домена `erp-library.md`, например: `applications` (заявки, проверка, архив), `billing` (счета, платежи, штрафы), `scheduling` (расписание, запись), `notifications` (письма, шаблоны), `chat`.
- События между сервисами через брокер (для стенда достаточно Redis Streams или RabbitMQ) и outbox.
- BPM: процесс заявки описан декларативно (BPMN или YAML-описание переходов), а не только в коде.
- Объём — такой, чтобы весь проект целиком помещался в контекст аудитора (ориентир до ~150 тыс. токенов кода и схемы). Иначе «жадный» аудитор сам не увидит всего.

### 1.2. Специально заложенные неочевидные связи

В каждой категории — минимум 2 случая. Каждый случай помечен в эталоне как `hidden: true`.

| Код | Категория | Пример из домена |
|---|---|---|
| H1 | Правило только в БД (CHECK, триггер, UNIQUE), в Python его нет | один действующий счёт за книги на заявку; запрет смены площадки после выдачи |
| H2 | Подписчик события в другом сервисе, импорта нет | «заявка оплачена» → закрытие дубля по той же сфере → аннулирование счёта дубля |
| H3 | Переход или guard только в описании BPM-процесса | «в долг» и социальная пропускают этапы счёта и оплаты |
| H4 | Поведение задаётся настройкой или справочником | заявка «в долг» использует шаблоны писем платных заявок |
| H5 | Фоновая задача или таймер | автоархив через месяц: точка отсчёта разная, сброс при возврате из архива |
| H6 | Неявный механизм ORM (event listener, cascade, `onupdate`) | событие в чат при смене этапа через listener SQLAlchemy |
| H7 | Транзитивная связь через другую сущность | обновление данных клиента → перепроверка **других** его заявок, не дошедших до записи |

### 1.3. Эталон (хранится отдельно от проекта)

```
eval/
  ground_truth/
    rules.yaml          # все правила: id, текст, где реализовано (file::symbol, constraint, topic, bpm-узел), hidden-категория
    edges.yaml          # связи: правило ↔ код ↔ таблица ↔ событие ↔ тест
    tasks/T01.yaml ...  # задачи и ожидаемый набор затронутых узлов
    doc_questions.yaml  # вопросы для проверки документации людьми/агентом
  hidden_tests/         # приёмочные тесты на побочные эффекты, агенту-исполнителю недоступны
  mutations/            # заготовленные изменения для проверки drift detection
  logs/                 # сюда пишет аудитор
```

**Изоляция обязательна.** Каталог `eval/` не должен попадать:
- в индексатор модели знаний;
- в Memory Bank;
- в память Ruflo;
- в рабочую копию агента-исполнителя (лучше отдельный репозиторий или каталог вне рабочего дерева).

Иначе исполнитель «подсмотрит» эталон или выводы аудитора, и метрики будут завышены.

## 2. Набор задач (golden tasks)

У каждой задачи есть эталонный набор затронутых узлов: правила, символы кода, таблицы и ограничения, события, BPM-узлы, тесты.

| ID | Задача | Какие скрытые связи должна найти |
|---|---|---|
| T01 | Разрешить смену площадки для социальной заявки после формирования ссылки на запись | H1 (CHECK), H2 (отмена записи → письмо), H4 (шаблон социальных на новой площадке), смена проверяющего оператора |
| T02 | Сократить срок пользования книгами с месяца до 21 дня | H5 (таймер срыва срока), штраф за просрочку, уведомление оператора |
| T03 | Разрешить частичную оплату с выдачей после 50% | H3 (переход к выдаче), H5 (автоархив по неоплате), дедупликация по моменту оплаты (H2), переплата |
| T04 | Для заявок «в долг» дедупликацию делать в момент оплаты, а не проверки | H2, H7, аннулирование счёта дубля |
| T05 | Добавить в данные клиента СНИЛС, обязательный для проверки | H7 (перепроверка других заявок), права проверяющего, событие в чате (H6) |
| T06 | Отдельные шаблоны писем для заявок «в долг» | H4, все места выбора шаблона |
| T07 | Разрешить администратору увеличивать максимум мест в окне задним числом | H1 (CHECK на места), уменьшение мест проверяющим оператором, уже записанные клиенты |
| T08 | Переименовать поле в ответе API чата (контрольная задача) | почти ничего: проверка, что pack не раздувается на локальных задачах |

T08 нужна, чтобы мерить precision и перебор контекста, а не только recall.

## 3. Варианты для сравнения

Каждую задачу прогоняем в нескольких вариантах. Каждый вариант — 3 повтора: LLM недетерминирована, без повторов разница в 10% ничего не значит.

| Вариант | Что есть у агента |
|---|---|
| B0 | Только код и схема БД, без документации и инструментов |
| B1 | «Куча md + grep»: документация в md, агент ищет сам |
| B2 | Полный контекст: весь проект и вся документация в окне (верхняя граница качества и стоимости). Эту роль может играть аудитор в «слепом» режиме, раздел 5.3 |
| S | Решение: модель знаний + MCP (`find_entry`, `impact`, …) + субагент-разведчик |
| S+MB | Решение вместе с Memory Bank и памятью Ruflo: проверяем, помогают они или мешают |

## 4. Метрики

**Д** — детерминированный подсчёт скриптом, **LLM** — нужна оценка аудитора. Целевые значения — стартовые ориентиры, их нужно уточнить после первого прогона.

### 4.1. Документирование (после bootstrap модели)

| Метрика | Как считать | Способ | Ориентир |
|---|---|---|---|
| Rule recall | доля правил эталона, найденных в модели | LLM-сопоставление → Д-подсчёт | ≥ 0.85 |
| Rule recall по hidden | то же, только для H1–H7, отдельно по категориям | LLM → Д | ≥ 0.75 в каждой категории |
| Rule precision | доля правил модели, которые верны (не выдуманы и не искажены) | LLM | ≥ 0.9 |
| Grounding | доля правил с `implemented_by`, где ссылка существует и действительно содержит эту логику | Д (существует) + LLM (содержит) | ≥ 0.9 |
| Edge recall | доля связей эталона (правило↔код↔таблица↔событие), которые есть в графе | Д | ≥ 0.8 |
| DB coverage | доля CHECK/UNIQUE/FK/триггеров, отражённых в модели | Д | 1.0 |
| Event coverage | доля пар издатель→подписчик, отражённых в графе | Д | ≥ 0.9 |
| Калибровка статусов | доля ошибок среди `verified` против доли среди `draft` | LLM | ошибок в `verified` ≈ 0 |
| Doc QA accuracy | агент отвечает на `doc_questions.yaml`, читая **только** сгенерированную документацию; доля верных ответов со ссылкой на страницу | LLM | ≥ 0.9 |
| Стоимость bootstrap | токены и время на шаги 3–5 bootstrap | Д | фиксируем |

### 4.2. Получение контекста (на каждую задачу)

| Метрика | Как считать | Способ | Ориентир |
|---|---|---|---|
| Entry hit@k | правильный узел среди top-k ответов `find_entry` | Д | hit@3 ≥ 0.9 |
| Impact recall | доля эталонных узлов задачи, попавших в context pack | Д (после сопоставления) | ≥ 0.85 |
| Hidden-link recall | то же, только для `hidden: true` — **главная метрика** | Д | ≥ 0.8 |
| Impact precision | доля элементов pack, относящихся к задаче | LLM | ≥ 0.6 |
| Размер pack | токены ответа `impact` | Д | ≤ 5 тыс. (заявлено в решении) |
| Токены на сбор контекста | токены до первого изменения файла | Д | ≥ 50% экономии к B1 |
| Токены всего | сбор + решение | Д | сравнение с B0/B1/B2 |
| Файлов прочитано целиком | число Read без offset/limit по файлам > N строк | Д | меньше, чем в B1 |
| Recall плана | доля эталонных правил, явно названных в плане агента | LLM → Д | ≥ 0.8 |

### 4.3. Результат изменения

| Метрика | Как считать | Способ | Ориентир |
|---|---|---|---|
| Task success | проходят видимые тесты и `hidden_tests` задачи | Д | сравнение с B0/B1 |
| Регрессии | упавшие `hidden_tests` других правил | Д | 0 |
| Обновление модели | PR содержит правку правил/аннотаций там, где поведение изменилось | LLM | ≥ 0.9 |
| Свежесть документации | после задачи документация отвечает на вопросы по изменённому правилу уже по-новому | LLM | 1.0 |

### 4.4. Сохранение контекста (drift detection)

Скрипт применяет заготовки из `mutations/` и прогоняет CI-проверки решения.

| Мутация | Ожидание |
|---|---|
| Изменена логика правила в коде, правило не тронуто | `suspect` + предупреждение |
| Логика перенесена во вспомогательную функцию (хэш исходного символа не изменился, поведение изменилось) | должно быть поймано; проверяет слабое место хэшей по одному символу |
| Новая миграция с CHECK без описания | блокировка PR |
| Переименован топик события у издателя, подписчик не обновлён | предупреждение |
| Только `ruff format` / переименование локальной переменной | **не** должно давать `suspect` |

Метрики: drift recall (доля пойманных значимых мутаций, ориентир ≥ 0.9) и false positive rate (ложные срабатывания на косметике, ориентир ≤ 0.1).

### 4.5. Дисциплина агента

| Метрика | Как считать |
|---|---|
| Compliance | доля сессий, где `find_entry` и `impact` вызваны **до** первого изменения файла (по логу MCP) |
| Использование статусов | доля планов, где `draft`/`suspect` правила отмечены как риск |

На текущем этапе исполнитель — только Claude Code. Проверка на Codex отложена.

## 5. Агент-аудитор в Ruflo

### 5.1. Роль

Аудитор — «оракул с полным контекстом». Он:
1. жадно читает всё: весь код всех сервисов, дамп схемы БД, BPM-описания, модель знаний, сгенерированную документацию, эталон из `eval/ground_truth/`, логи MCP-сервера и транскрипты сессии исполнителя;
2. сопоставляет узлы модели с узлами эталона (это единственная операция, где нужна семантика);
3. считает метрики раздела 4;
4. пишет результат в JSONL-лог и краткий отчёт.

### 5.2. Правила, без которых метрики будут недостоверны

- **Только чтение.** Аудитор не правит проект, модель и документацию.
- **Запуск после сессии исполнителя**, а не параллельно с ней.
- **Выход не попадает в память.** Логи пишутся в `eval/logs/`, этот путь исключён из Memory Bank, памяти Ruflo и индексатора модели. Иначе на следующей задаче исполнитель получит выводы аудитора через память, и recall вырастет искусственно.
- **Отдельная сессия без общей памяти.** И исполнитель, и аудитор — Claude, поэтому есть риск, что модель завысит оценку работы, похожей на её собственную. Снижаем его так: у аудитора всегда новая сессия с пустым конфигом, своя модель (самая сильная доступная, `--model` задаётся явно), он не видит рассуждений исполнителя (только план, diff и логи), каждое суждение подкреплено `evidence`. На выборке можно прогнать второго судью на другой модели Claude: если судьи расходятся, суждение смотрит человек.
- **Всё, что можно, считает скрипт.** LLM только сопоставляет узлы и оценивает precision/корректность. Каждое LLM-суждение пишется в лог с `evidence` (file:line), чтобы его можно было проверить.
- **Проверка самого аудитора.** На первом прогоне 15–20% LLM-суждений проверяет человек. Если согласие ниже ~90%, промпт аудитора правится до того, как его оценкам можно доверять.

### 5.3. Два режима

| Режим | Что видит | Зачем |
|---|---|---|
| `blind` | всё, **кроме** эталона | сам делает impact-анализ задачи с полным контекстом: это вариант B2 и одновременно проверка эталона (если аудитор нашёл связь, которой нет в эталоне, — эталон неполон) |
| `score` | всё, включая эталон | считает метрики исполнителя |

### 5.4. Формат лога

Файл `eval/logs/<run_id>/audit.jsonl`, одна строка — одно измерение:

```json
{"ts":"2026-10-22T14:03:11Z","run_id":"r017","task_id":"T01","variant":"S","repeat":2,
 "worker_model":"claude-opus-5-5","auditor_model":"claude-opus-5-5","mode":"score",
 "phase":"context","metric":"hidden_link_recall","value":0.75,
 "expected":["H1:chk_venue_change_allowed","H2:scheduling.booking_cancelled","H4:tpl_social_cancel","R-CHECKER-REASSIGN"],
 "found":["H1:chk_venue_change_allowed","H2:scheduling.booking_cancelled","R-CHECKER-REASSIGN"],
 "missed":["H4:tpl_social_cancel"],
 "method":"deterministic","evidence":["notifications/templates.py:41"]}
```

Плюс `eval/logs/<run_id>/summary.md` — таблица метрик по вариантам и список пропущенных связей с объяснением, почему pack их не дал (нет узла в модели / нет ребра / неверная точка входа / обрезка по глубине).

**Классификация причин пропуска важнее самой цифры recall:** она показывает, какую часть решения чинить.

### 5.5. Источники данных для аудитора

| Что | Откуда |
|---|---|
| Вызовы `find_entry`/`impact`, размер ответов, время | лог MCP-сервера (заложить с первого дня: tool, args, ответ, токены, session_id) |
| Токены исполнителя | транскрипт headless-запуска Claude Code (`--output-format stream-json`, поле usage) |
| Изменения | `git diff` ветки задачи |
| Тесты | junit-отчёт pytest по видимым и `hidden_tests` |
| Drift | вывод CI-проверок решения на мутациях |

### 5.6. Черновик определения агента

Формат ниже — markdown с frontmatter, как у агентов Claude Code (`.claude/agents/*.md`). Ruflo (бывший claude-flow) использует похожий формат, но формат и способ запуска по хукам (`post-task` / `session-end`) нужно сверить с документацией установленной версии Ruflo.

Определение аудитора хранится **только в репозитории стенда**: `library-eval/agents/context-auditor.md` в формате агента Ruflo, зарегистрирован в Ruflo стенда симлинком `library-eval/.claude/agents/eval/context-auditor.md`. Ruflo стоит локально в `library-eval` (закреплённая версия 3.59.7, автообновление выключено). Итог каждого аудита пишется в память Ruflo стенда (`library-eval/.swarm`, пространство имён `audit`) отдельной командой после сессии; сам аудитор память не читает — работает в клоне проекта без хуков Ruflo, чтобы аудиты оставались независимыми. Если положить его в `.claude/agents/` проекта, исполнитель увидит описание эталона и метрик.

У аудитора нет инструментов записи и Bash. Результат он печатает в stdout строками JSONL, а раннер дописывает их в лог. Так аудитор физически не может изменить проект.

```md
---
name: context-auditor
description: Read-only auditor. Reads the whole project, knowledge model, docs, ground truth and worker logs; computes documentation and context-retrieval metrics; prints JSONL to stdout. Run only after a worker session finishes.
tools: Read, Grep, Glob
---

Ты — аудитор качества документирования и доставки контекста. Ты ничего не изменяешь в проекте.

Вход: RUN_ID, TASK_ID, VARIANT, MODE (blind | score).

1. Прочитай целиком: код всех сервисов, дамп схемы БД, BPM-описания, knowledge/, сгенерированную документацию.
   В режиме score дополнительно: ground_truth/, лог MCP-сервера, транскрипт сессии исполнителя, diff, junit-отчёты
   и детерминированные метрики, уже посчитанные раннером (audit.jsonl прогона).
2. Сопоставь узлы модели с узлами эталона. Для каждого сопоставления укажи evidence (file:line). Сомнительные пометь "uncertain".
3. Детерминированные метрики не пересчитывай. Сам оценивай только то, что помечено LLM в evaluation_plan.md.
4. Для каждого пропущенного эталонного узла определи причину: no_node | no_edge | wrong_entry | depth_cutoff | agent_ignored_pack.
5. В режиме blind сделай собственный impact-анализ задачи и перечисли связи, которых нет в эталоне.
6. Выведи каждое измерение отдельной строкой JSONL по схеме из evaluation_plan.md, затем строку ---SUMMARY--- и краткий итог в markdown.
Ничего не изменяй в файлах.
```

## 6. Протокол прогона

1. Сгенерировать проект и эталон. Прогнать аудитора в режиме `blind` по всем задачам, дополнить эталон найденными связями. Человек проверяет дополнения.
2. Bootstrap модели знаний по решению → метрики 4.1.
3. Для каждой задачи × варианта × 3 повтора: исполнитель решает задачу в чистой ветке и чистой сессии → аудитор `score` → метрики 4.2–4.5.
4. Прогон мутаций → метрики 4.4.
5. Сводка: таблица вариантов, разброс по повторам, причины пропусков.
6. Повторить шаги 3–5 после серии из 5–10 задач подряд **без** пересборки модели вручную: так проверяется, что модель не деградирует в обычном рабочем цикле.

## 7. Какие утверждения решения проверяет стенд

| Утверждение в решении | Метрика |
|---|---|
| Граф находит связи, которые grep пропускает | hidden-link recall: S против B1, по категориям H1–H7 |
| Context pack 2–5 тыс. токенов вместо десятков файлов | размер pack, токены на сбор контекста |
