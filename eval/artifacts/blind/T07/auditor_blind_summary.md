Плюс тесты на увеличение, уменьшение, окна проверяющего, прошедшие окна и другие площадки. Миграция по формулировке задачи не нужна.

Что легко пропустить:
- **Порядок записи в БД.** Триггер `trg_slot_capacity_limit` (`migrations/versions/0001_initial.py:259`) сверяет новый `capacity` с `scheduling.venue_limits`. При увеличении максимума лимит должен попасть в БД раньше UPDATE окон: например, Core `update(Slot)` после присваивания `limit.max_capacity` (сработает autoflush) или явный `flush()`. Если менять объекты Slot через ORM, порядок записи двух несвязанных таблиц не гарантирован.
- **Окна проверяющего не помечены.** Их отличает только `capacity < old_max` (`reduce_capacity` уменьшает строго). Окно, созданное с явным `capacity`, равным максимуму, обновится как обычное.
- **Переполненные окна.** При уменьшении максимума окно может оказаться с числом записей больше нового `capacity` — нужно явное решение. Если выбрать отмену записей, по цепочке `booking.cancelled` сработают письма и чат.
- **Две копии максимума.** `Venue.max_slot_capacity` и `VenueLimit.max_capacity`. Старое значение лучше брать из payload, тогда повторная доставка из Redis Streams безопасна.
- BPM-процесс заявки и фоновые задачи эта задача не затрагивает.
